# 默认审查的职责调整与五轮验证

2026-09-09。目标是可解释、有实际跨 diff 取证能力的求职项目，不以扩大提示词和模型调用次数模拟生产级静态分析。

## 为什么此前只改 ReAct 没有解决问题

1. **初筛成了召回瓶颈。** DirectTriage 只拿 diff/符号目录，却先决定值得调查的问题，后续执行者只能围绕这些问题工作。运行时无法保证初筛遗漏的变化会得到审查。
2. **模型接口被兼容字段污染。** CandidateSeed/CoverageDeclaration 中的 `mechanism_note2`、`confidence_note2` 等历史占位字段通过继承进入 provider schema；模型为这些字段生成文字。新的默认路径不再暴露这些模型，旧兼容模型保留在旧路径。
3. **获取基础上下文也要模型决策。** 多次调用只是读取变更方法、再读所属类寻找某个成员 ID。初次审查没有源码，后续花轮数导航，且多份调查重复探索。
4. **非证据协议消耗预算。** 前两轮新实验各有三次决策纠错，都是 observation_refs 已读回执的格式问题。已读回执不是证据，已从默认 schema 移除；最终 finding 的真实证据引用仍严格验证。
5. **评测和入口也需要核对。** 旧 `eval-codeguard-full` 指向历史 react，和 CLI 默认受控路径不一致。部分正式标答把等价修改或没有证实的行为变化标成 bug。不能把这些漏报全部归咎于执行器。

已检查 runner 的干净基线校验、应用 diff 的临时 workspace、session revision 和 task patch 传递。没有证据表明这批结果由统一的 diff 方向/快照反转造成；不能由此宣称所有仓库快照都已逐字复验。

## 当前默认路径

```text
diff → task/DirectGate → SymbolResolution
     → 变更声明分组 → 源码与有界一跳关系准备 → 同一 Reviewer 阅读、按需查询、提交候选
     → 确定性定位/证据绑定 → EvidenceVerifier → 批量 Judge → 合并结果
```

- 主入口：`pipeline/controlled/change_review.py`。每组最多四个实际变更声明，按位置确定性分组；空白新增行不会额外触发整个类型。删除变更使用当前版本锚点。不会先遍历全项目所有 symbol。
- 默认不执行知识路由 Plan、Summary、DirectTriage、模型 GraphPlan。`planned_steps` 和历史 `react` 仍是显式兼容路径；未来清理归档可以独立进行，不让旧模型接口进入默认调用。
- 同一 Reviewer 从源码开始理解变更，不先接受预判 bug。少量根符号、真实导航、预算和证据合同约束执行；语义判断仍可能错误。
- 默认每组最多六次探索、八次工具尝试，加一次预留结论；每 task 总工具预算 32。源码准备最多占工具额度一半，各源片段最多 120 行并受 Gateway 字节限制。源码和一跳关系合计预取最多 `budget - min(budget, max(2, budget // 3))` 次，默认最多六次，至少保留两次动态查询机会。预取/拒绝都计预算，各组共享 HTTP 缓存但不共享本地 Txx 编号。
- 一跳预取从变更声明出发：方法/构造器查 callers/callees，字段查 readers/writers，类型查 implementations。先跨根符号分配第一个方向，再分配第二个方向；每页最多六个关系结果并请求端点源码。不自动追游标、不展开返回端点，不能称为完整邻域。`preparation_scope` 明确未查询关系，真实响应继续携带 coverage/limitations/next_cursor；只有工具原文是 Txx 证据，范围清单不是事实。
- 首轮直接使用预取的 Txx，继续取证与终止沿用同一个决策协议，不增加直审/规划 LLM。预取在子任务超时内执行；超时后禁止首次模型调用。自动预取的空关系仍关闭对应入口，但不计入模型的全局无进展计数；模型循环开始后沿用原空转护栏。
- Java `read_symbol` 为方法/字段同时返回所属类型的有界成员目录，免去只为寻找 ID 而读取类的额外调用。目录只来自索引，不推断调用边；不为源码读取隐式启动整项目语义展开。继承成员与外部库仍可能查不到。
- 默认模型输出 assessment 与 queries/result，不生成旧初筛兼容字段或已读回执。结果最多八个候选，每条最多三条真实观察。局部问题可只绑定 patch，跨符号主张需要实际源码/关系支持。
- 原对话预留结论，关闭后不再执行查询；格式纠错也使用原预算。未知最终观察编号在终止前反馈，不静默删掉未知引用再放行。
- 定位复用已有 Locator，新增片段唯一匹配可修正行号；纯删除使用传入锚点，失败保留文件级候选。受控路径不为定位额外调用模型。
- Artifact 使用原 task patch 摘要，展示截断不能改变 revision 身份。截断、无符号、结果 limitations 和预算省略保留未完成状态，已经有候选不代表整个组完成。
- `eval-codeguard-full` 与 `eval-controlled-codegraph` 现在都指向 `orchestration=change-review`。旧同名 archive 不可当成同一配置做趋势对比。

Java CI 调度/MySQL 持久化与恢复（测试使用 H2）、Tool Server 沙箱与语义图、LLM Proxy 路由/熔断继续保留原边界。问题不是需要推翻后端，而是让事实基础设施服务于更少的模型分工。

## 尚未解决的限制与取舍

- 模型仍可能偏重某个变更、误读算法、追求不必要的消费者证明。分组确保进入审查，不保证发现每个问题。
- 单组最多四个声明是简单预算取舍，并非语义独立性的证明；共享大方法/文件背景可能产生重复，或让弱模型分散注意力。
- 源码分页、继承接口、构造器初始化和库外依赖仍会形成缺口；成员目录不能替代完整的类型/数据流分析。
- 预留结论是执行兜底。五轮中仍有五组使用它，不能声称已消除预算收口或所有无效调用。
- 五轮之间的变化依次包含：源码起步/去掉前置模型、空白行分组与限制状态、成员目录与去掉已读回执、候选定位与最终引用校验。最后的删除锚点、跨 task 唯一组 ID、截断摘要一致性和 profile 对齐只做离线验证。
- 最值得投入的下一步是冻结这一简化路径，人工复核评测标签，再用少量明确需要 diff 外证据的 case 做固定配置对照；不能继续为可疑标答扩大 ReAct 提示词或工具预算。

适合项目介绍的亮点是“变更驱动的有界 agent、按需语义图、真实证据溯源、失败与未完成分层、可复现的质量审计”，而不是未经证明的高召回百分比。
