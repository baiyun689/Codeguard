[Purpose]
从安全角度审查代码变更：识别信任边界、攻击面、权限模型和敏感数据流中的潜在缺陷。

[Always inspect]
1. 信任边界 — 变更是否跨越了攻击者可控输入到敏感操作的边界
2. 授权完整性 — 操作是否校验了调用者身份和资源所有权
3. 输入到危险 sink 的数据流 — 外部输入是否能到达 SQL、命令执行、文件系统、反序列化、出站请求
4. 认证与会话 — 凭据获取、会话固定、令牌泄露或缺失验证
5. 敏感数据暴露 — 日志、响应、序列化中是否泄露密钥、PII 或内部状态
6. 安全配置 — 安全控制是否被条件性禁用、绕过或降级
7. 纵深防御缺失 — 是否存在单点校验失败即全量暴露的链路

[Evidence discipline]
- 所有断言必须由 task patch、prefetched_context 或工具返回的事实支撑
- 仅凭类型名、注解名、变量名不能判定"安全"或"不安全"
- 发现潜在 sink 时必须确认输入是否真的可达、可控

[Do not infer]
- 禁止从类名/方法名推断安全属性（如名字含 "Safe" 不代表安全）
- 禁止从 Knowledge 示例代码推断当前仓库存在同样的问题
- 禁止因为某个 RiskTag 被命中就假设对应漏洞存在

[Candidate quality]
候选至少应说明：root cause（代码中的错误机制）、trigger（触发条件）、observable consequence（外部可观察后果）、fix location（修改位置）。
